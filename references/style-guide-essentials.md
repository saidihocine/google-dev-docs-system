# Google Developer Documentation Style Guide — Essentials

This is a condensed operating version of the official Google developer documentation style guide. Use it as the default filter for all writing and reviews.

## Tone and Content
- Be conversational and friendly without being frivolous.
- Do not pre-announce future features in documentation.
- Use descriptive link text (never "click here" or "this page").
- Write accessibly.
- Write for a global audience (clear, simple, translatable language).

## Language and Grammar
- Use second person: "you" rather than "we".
- Use active voice: make clear who performs the action.
- Use standard American spelling and punctuation.
- Put conditions before instructions.
- Prefer present tense for describing API behavior.

## Formatting and Organization
- Use sentence case for document titles and section headings.
- Use numbered lists for sequences of steps.
- Use bulleted lists for most other lists.
- Use description lists for pairs of related data.
- Use serial commas.
- Put UI elements in **bold**.
- Use unambiguous date formats.

## Images and Media
- Provide meaningful alt text for every image.
- Prefer high-resolution or vector images when practical.

## API Reference Specifics
- Every class, interface, method, parameter, field, constant, and return value must have a description.
- Descriptions should be concise, informative, and in present tense.
- Include a short working code sample near the top of reference pages when useful (~5-20 lines).
- Link API names to their reference pages.

## Hierarchy of Authority
1. Project-specific style (if any)
2. This Google Developer Documentation Style Guide
3. Merriam-Webster (spelling), Chicago Manual of Style (non-technical), Microsoft Writing Style Guide (technical, with judgment)

## Override Rule
Break any of these guidelines sooner than produce unclear or unhelpful content. When you depart, remain consistent within the document.
